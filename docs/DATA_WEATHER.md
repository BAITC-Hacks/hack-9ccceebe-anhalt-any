# Данные и погода — передача A → B/C

Ветка `feature/data-weather`. ML-модули, артефакты, оркестратор и подтверждения
организаторов не изменяются. Оба CLI работают только при явном запуске.

Проверено на реальных файлах: 50 784 строки истории; 58/58 запросов ECMWF на 80 м,
2 784 погодные строки без пропусков. Все 58 запросов повторно прочитаны из кэша с
отключённым HTTP. Хеши, координаты ячеек и ограничения сохранены в
[отчёте проверки](../reports/data_weather_validation.json).

## Быстрый запуск

Из корня репозитория, после установки `requirements.txt`:

```bash
python scripts/prepare_data.py
python scripts/cache_weather.py --start 2026-01-31 --end 2026-01-31 --turbine T1
python scripts/cache_weather.py --mode runs --start 2026-01-31 --end 2026-02-28 --height 80
python -m pytest -q tests/test_data_pipeline.py tests/test_data_weather.py
```

Последняя погодная команда делает 58 запросов: 29 дней × T1/T2, выпуски **00 UTC**,
по 48 часов от инициализации. Это проверка/подготовка архива, **не 58 исторических
прогнозов, допустимых на 00 UTC**. Повторный запуск читает локальный кэш.
`--run-hour 6|12|18`, `--horizon 24|48`, `--height 80|100`, `--turbine T1|T2`
позволяют менять выборку. `--refresh` запрашивает API заново; изменившийся известный
ответ не перезаписывает прежний. Нет автоматической замены ошибочного ответа кэшем.

## История

```python
from src.data.loader import load_historical_data
from src.data.features import build_features

df = load_historical_data()
X = build_features(df)
assert len(X) == len(df)
# y = df['power'] остаётся в неподтверждённых исходных единицах.
```

По умолчанию читается полученный `historical_hourly.csv` из
`data/goldwind/incoming/received_20260923/`. Поддерживаются путь, список CSV или
явное соответствие `{'T1': path1, 'T2': path2}`. Параметр `columns` задаёт
переименование исходных колонок; `temp` автоматически становится `temperature`.
`timezone` задавайте только после подтверждения. Без него naive время остаётся
naive, с предупреждением. Противоречивые дубликаты и неверное время вызывают ошибку.

Выход: `datetime,turbine_id,wind_speed,temperature,power`, `sample_count`, ссылки на
исходные строки и флаги качества. Точные дубликаты удаляются с записью количества.
Нечисловые/бесконечные значения становятся NaN с флагом и сохранением исходного
текста; подозрительные физические значения сохраняются. Пропуски не интерполируются,
мощность не умножается на 2500 и не ограничивается номиналом.

В поставке 50 784 строки за 11.03.2023–31.01.2026, по 25 392 на турбину.
`complete_samples` означает ровно 6 исходных измерений за час; это проверка
полноты предоставленной агрегации, не подтверждение корректности её семантики.
`missing_measurement` отмечает NaN хотя бы в одном из трёх измерений.
Решение об исключениях из обучения принимает B с учётом всех флагов.

CLI создаёт `data/processed/historical_clean.csv`, `historical_features.csv` и
`manifest.json` с хешами исходников и оставшимися неопределённостями. CSV признаков
содержит ключи времени/турбины для соединения; они не входят в числовой `X`.

## Признаки и граница ML

`src.data.features.build_features(df)` возвращает 9 числовых колонок в порядке:
`wind_speed, temperature, hour, month, day_of_year, sin_hour, cos_hour, sin_month, cos_month`.
Индекс и порядок строк сохраняются. Календарь использует timezone переданных меток;
функция не угадывает локальное время. NaN остаются видимыми, imputer обучает B только
на обучающем периоде. Power, его лаги и признаки из присланного derived CSV не используются.

Опциональные `include_lags=True, forecast_origin=...` разрешены только для одного
погодного выпуска, доступного к origin. Это лаги **архивного погодного прогноза**,
не фактических наблюдений будущих часов. Смещения 1/3 часа и rolling 3 часа считаются
по часовой сетке с `shift(1)` перед rolling; разрывы не заполняются прошлой строкой.
По умолчанию лаги выключены, для наблюдаемой истории этот режим запрещён.

Для строгого сценария C после подтверждений может указать
`FORECAST_DATA_MODULE=src.data.weather`. Его `get_forecast_weather` возвращает
aware DatetimeIndex, `wind_speed_ms,temperature_c,wind_direction_deg`, времена
выпуска/доступности и provenance. Его **отдельный** `build_features` возвращает
ровно `wind_speed_ms,temperature_c`, без календаря. Целевая модель B должна объявить
эти два признака в manifest и сама выполнять сохранённую обработку; если B выберет
схему из 9 признаков или направление, требуется согласовать адаптер и manifest.
Готовый Kelmarsh artifact не подходит для T1/T2 и этим модулем не подключается.

## Архивная погода и историческая доступность

```python
from src.data.weather import fetch_weather_run, get_archival_weather

# Реальный API, без доказательства исторической доступности:
run = fetch_weather_run(43.645150, 78.535604, '2026-01-31T00:00:00Z', 48)

# Строгий публичный интерфейс, после заполнения политики на основании источника:
# weather = get_archival_weather(43.645150, 78.535604, origin_with_timezone, 48)
```

Оба интерфейса возвращают колонку `datetime`, `wind_speed` в м/с, `temperature`
в °C, `wind_direction` в градусах и флаг пропусков. Используется только
`single-runs-api.open-meteo.com`, явно `models=ecmwf_ifs`; ветер по умолчанию 80 м,
температура 2 м. 100 м доступно явно. Автоматического перехода на 10 м нет.
Высота 80 м — переменная API с обработкой высоты на стороне Open-Meteo, а не
заявление о native уровне модели или высоте датчика SCADA. Сохраняются координаты
выбранной погодной ячейки; две близкие турбины могут попасть в одну ячейку.

У Single Runs `run` обозначает инициализацию; она предшествует публикации.
Документация также описывает архив ECMWF начиная с марта 2024 как IFS 49R1 hindcasts.
Поэтому наличие ответа за февраль и типичная задержка 4–6 часов **сами по себе не
доказывают**, что именно этот ответ был доступен в тот день.
[Источник: Single Runs API](https://open-meteo.com/en/docs/single-runs-api).

`fetch_weather_run` помечает результат `archive_run_unverified`, не выставляет
`weather_available_at`. В `get_archival_weather` параметр `run_date` — aware
**forecast_origin**. Функция выбирает последний допустимый выпуск и возвращает
ровно 24/48 часов от origin + `first_lead_hour` (по умолчанию 1). Single Runs на
живой проверке отклоняет `start_hour`; клиент запрашивает `forecast_hours` от
инициализации до конца нужного окна и выбирает часы, проверяя временную сетку.

Строгий вызов по умолчанию останавливается до HTTP: файл
`config/weather_availability.template.json` намеренно не подтверждён. Политика требует:

- `confirmed=true`, `covers_archived_revision=true`, модель, диапазон origin и
  реальное основание `evidence`, покрывающее **конкретную архивную версию**;
- `basis=documented_delay` и подтверждённую задержку `delay_hours` 1–24 часа, либо
  `basis=publisher_timestamp` и `runs` с реальными временами и хешами ответов.

Формат записи `runs`: `issued_at`, `available_at`, `payload_sha256`, `request`.
В `request`: `latitude,longitude,forecast_origin,horizon_h,first_lead_hour,wind_height_m`.
`forecast_origin` нормализуется в UTC ISO с `+00:00`; `payload_sha256` берётся из
атрибутов проверяемого запроса. Простое копирование сегодняшнего хеша не заменяет
доказательство публикации того же содержания в прошлом. Код проверяет утверждения
и непротиворечивость, но не может удостоверить источник вместо человека.

После подтверждения времени запуска организаторами и политики источника:

```bash
python scripts/cache_weather.py --mode origins --timezone "$CONFIRMED_TIMEZONE" \
  --origin-hour "$CONFIRMED_HOUR" --availability-policy path/to/confirmed-policy.json
```

Для строгого оркестратора отдельно нужен подтверждённый `FORECAST_PROTOCOL_PATH`.
Данные кэширования `runs` и `origins` имеют разные ключи окна. Для изменённой версии
архива нужна новая доказанная доступность и отдельная директория кэша.

## Надёжность и ограничения

Timeout 30 с, максимум 3 попытки (настраивается 1–5), интервал запросов 1 с,
повтор только при timeout/connection error, HTTP 429/5xx. Длительный `Retry-After`
останавливает попытки. Ошибки JSON, единиц, времени, пустые/полностью отсутствующие
измерения не кэшируются. Частичные пропуски сохраняются с флагами.
Кэш проверяет SHA-256 и записывается атомарно без перезаписи известного содержимого.
Его ключ включает координаты, выпуск, окно, горизонт, модель, единицы и высоту.
HTTP-тесты используют mock и не требуют сети. API-ключ для этих запросов не нужен.

`data/processed/` и `data/weather_cache/` исключены из Git. Для передачи кэша его
можно копировать отдельно; воспроизводимая команда и исходные CSV находятся в Git.

Открыты: timezone и смысл timestamp истории, нормализация power, принадлежность
исходных файлов T1/T2, высота датчика, публикационная задержка SCADA; история
фактической мощности февраля отсутствует. Погодные значения API instantaneous,
а SCADA экспорт агрегирован по часам: способ приведения должен быть согласован
и одинаков при обучении/прогнозе.
[Определения переменных Open-Meteo](https://open-meteo.com/en/docs).
Эти ограничения не позволяют объявлять точность целевого прогноза или 100% соответствие ТЗ.
