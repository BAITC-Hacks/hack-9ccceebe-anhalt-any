## Что остаётся неизвестным

1. Timezone и историческая политика перевода часов: datetime записан без offset.
2. Начало/конец часовой ячейки и исходных 10-минутных интервалов, метод агрегации.
3. Формула normalized power и её знаменатель. Умножение на 2500 пока было бы гипотезой.
4. Реальная идентичность T1/T2. В полученном quality report прямо сказано, что метки
   назначены по порядку загрузки файлов и могут требовать перестановки.
5. Высота/место измерения ветра и возможная предварительная обработка. Высота ступицы
   80 м не доказывает происхождение поля wind_speed.
6. Время доступности SCADA и подтверждённое расписание первого исторического origin.
7. Исходные файлы и код агрегации, источник/версия и любые удаления/обрезки мощности.

`confirmed` в forecast protocol остаётся false. Получение CSV снимает отсутствие табличной
истории, но не подтверждает эти определения и не создаёт модель автоматически.

## Для Person B

Основной полученный файл: `data/goldwind/incoming/received_20260923/historical_hourly.csv`.
Предлагаемое соответствие названий: datetime → timestamp; wind_speed → wind_speed_ms;
temp → temperature_c; power → целевая переменная в ИСХОДНЫХ единицах. Названия ещё не
подтверждают единицы. Сохранять turbine_id и sample_count.

Вход уже агрегирован. Нельзя передавать каждую строку как полноценные 60 минут в существующий
raw-interval loader: он не проверяет sample_count и принял бы неполный час за полный.
Нужен отдельный импорт агрегатов с явным фильтром покрытия, сохранением исключённых строк
и подтверждённой семантикой. Для первичной проверки выделены 48 452 строки с sample_count=6;
их фактическая пригодность зависит от подтверждения исходных интервалов и очистки.

Не использовать все колонки `historical_hourly_features.csv` автоматически. Файл содержит
power_lag_* / power_roll_* и лаги наблюдаемого ветра. Проверенные rolling значения сдвинуты
на один час и не включают текущую строку, однако это не делает их доступными сразу для
48-часового прогноза. Например, power_lag_1h для valid_time=02:00 требует факта 01:00,
которого нет при origin=00:00. Любая такая фича требует отдельного point-in-time контракта
или честного рекурсивного расчёта. В текущем weather-only pipeline их не подключать.

После подтверждения определений: временной split до первого origin, отдельная проверка
предобработки/подбора, baseline и целевая модель. Февраль не использовать для обучения
или подбора. Метрики по наблюдаемому ветру маркировать MODE A; это не качество прогноза
по погодному архиву. Для integration вернуть raw 1D кВт и строгий model manifest.

## Для Person A

`weather_requests_manifest.csv` содержит 58 URL: 29 дней × 2 турбины, горизонт 48 часов.
Ответов API, погодных значений, фактических выпусков и времени доступности в поставке нет.
Поля `models` нет ни в одном URL, поэтому требуемая модель источника явно не зафиксирована.

Проверена официальная [документация Single Runs API](https://open-meteo.com/en/docs/single-runs-api):
run обозначает инициализацию модели, а не доступность результата. Для глобальных моделей
описана обычная задержка расчёта порядка 4–6 часов. Документация указывает архив ECMWF IFS
с марта 2024, остальных моделей — с апреля 2026. Для февраля нужно явно выбрать подходящий
продукт и подтвердить историческую доступность конкретной версии. Эти сведения сами по
себе не подтверждают получение любого из 58 запросов и не разрешают считать run=origin.

Полученный `weather_api.py` не подключён и не выполнялся. До интеграции требуется:

- Реализовать get_forecast_weather/build_features по TARGET_FORECAST_CONTRACT.md: aware
  DatetimeIndex, wind_speed_ms/temperature_c, kind/source/height и evidence доступности.
- Разделить origin, инициализацию, публикацию и valid_time. Выбирать выпуск по availability,
  не обнулять переданный origin до полуночи. Покрыть нужные часы после origin, а не просто
  первые 48 строк выпуска; старшему выпуску может потребоваться более длинный запрос.
- Зафиксировать model/product и происхождение ветра на 80 м; проверить возвращённые units.
- Сохранять actual weather_issued_at/weather_available_at и происхождение при чтении кэша.
- Получить хотя бы один реальный ответ и доказательства его доступности, затем все origins.
  Не подменять missing API cache реанализом или наблюдениями.

Без подтверждённой задержки публикации/архивной ревизии strict readiness сохраняет блокер.
