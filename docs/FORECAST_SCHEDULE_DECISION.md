# Решение команды: первый запуск и календарь прогнозирования

По поручению пользователя от 23 сентября 2026 года интегратор выбирает расписание
как инженерное решение команды. Дополнительного согласования первого origin с C
не требуется. Это не утверждение о timezone исходных CSV и не ответ организаторов.

| Параметр | Принятое значение |
| --- | --- |
| Календарь запусков и выходных интервалов | `Asia/Almaty` |
| Первый forecast_origin | **`2026-01-31T23:00:00+05:00`** |
| Тот же момент в UTC | **`2026-01-31T18:00:00Z`** |
| Ежедневный запуск | 23:00, с 31 января по 28 февраля включительно; 29 origins |
| Первый прогнозный час | origin + 1 час |
| Первый целевой интервал | `[2026-02-01T00:00:00+05:00, 2026-02-01T01:00:00+05:00)` |
| Горизонты | 24 и 48 почасовых интервалов |
| Оценочный период | `[2026-02-01T00:00:00+05:00, 2026-03-01T00:00:00+05:00)` |

Так первый прогноз, выпущенный 31 января, покрывает весь следующий календарный
день. Горизонт 48 часов покрывает 1 и 2 февраля; обе последовательности запусков
покрывают все 672 часа февраля. Прогнозы на март сохраняются, но не оцениваются
в февральском окне. Перекрывающиеся origins остаются отдельными прогнозами.

Это расписание проекта, выбранное из разрешённого ТЗ диапазона 24–48 часов.
Если организаторы зададут другой календарь оценки, решение надо явно пересмотреть
и повторить обучение/проверку cutoffs, кэширование и replay, а не переименовать метки.

## Передача B

В `config/goldwind_dataset.template.json` заполнены `first_forecast_origin` и
`forecast_origin_source`. Обязательная граница для fit, preprocessing, настройки
и выбора модели: **данные доступны не позднее `2026-01-31T18:00:00Z`**.
Проверять одновременно `interval_end <= origin` и `available_at <= origin`.
Строки с датой 31 января не становятся автоматически допустимыми.

Пример только для иллюстрации: если исходные данные действительно имеют timezone
Asia/Almaty и метку начала часа, интервал 31 января 23:00–00:00 ещё не завершён
к первому origin и исключается. Интервал 22:00–23:00 допустим только при публикации
не позднее 23:00; при положительной задержке он тоже исключается.

Timezone исходных файлов остаётся `null`. После его подтверждения временные метки
переводятся в UTC для сравнений и в календарь проекта для согласованных признаков.
Исходные начало/конец интервала и единицы также требуют подтверждения; смена
расписания не разрешает молча локализовать CSV или умножить power на 2500.
Время источника и календарь модели должны храниться отдельно: после явного
преобразования календарные признаки и `model manifest.timezone` согласуются с
`Asia/Almaty` в прогнозном протоколе. Исходная timezone сохраняется в provenance.

## Передача A/C

`config/forecast_protocol.json` содержит выбранные timezone и час запуска, но
`confirmed=false` сохраняется до подтверждения семантики исходных данных и target.
Машиночитаемое решение о расписании лежит отдельно в `config/forecast_schedule.json`.
Схемы/интерфейсы ML и оркестратора не изменены.

На первом origin нужны погодные выпуски с issue и фактической availability не
позднее 18:00 UTC 31 января. Конкретный run выбирает подтверждённая политика
источника; origin нельзя приравнивать к инициализации погодной модели. Скачанный
00 UTC архив сам по себе не является готовым кэшем для этого календаря и не
доказывает историческую доступность.

После выполнения остальных условий команда первого расчёта:

```bash
python scripts/run_target_forecast.py --origin 2026-01-31T23:00:00+05:00 --horizon 48
```

Старый пример `2026-01-31T23:00:00Z` обозначает другой момент и для принятого
расписания не используется. Сохранённые прежние отчёты остаются историческими.
