# AI Energy Agent

HackAlem AI 2026 · Anhalt ANY

Агент помогает анализировать прогноз генерации двух ветрогенераторов Goldwind GW109/2500.
Мощность рассчитывает локальная ML-модель. LLM объясняет результат и флаги правил,
но не рассчитывает и не изменяет основной прогноз.

**Текущий статус:** реализован строгий основной сценарий T1/T2 с контролем времени
доступности данных, rolling replay февраля, суммой станции и пересчётом при обновлении
входов. **Получена почасовая история с метками T1/T2:** 50 784 строки за
11.03.2023–31.01.2026. Файлы сохранены в `data/goldwind/incoming/received_20260923/`.
**Реальный прогноз пока заблокирован:** timezone, метки интервалов, идентичность турбин,
нормализация и высота измеренного ветра не подтверждены; целевая модель и проверенный
архив погодных выпусков не подключены. [Аудит и передача A/B](docs/GOLDWIND_DELIVERY_REVIEW.md).
Наличие кода и тестов не означает успешный запуск на целевых данных.
Подключён загрузчик B (PR #3); полученный агрегированный CSV требует отдельного разбора sample_count и подтверждения метаданных перед обучением.

Добавлен модуль A: очистка полученной истории с флагами `sample_count`, календарные
признаки, клиент Single Runs ECMWF и проверяемый локальный кэш. Подготовка:
`python scripts/prepare_data.py`; архив выпусков:
`python scripts/cache_weather.py --mode runs`. Этот режим скачивает конкретные
выпуски, не подтверждая их доступность в прошлом. Публичный интерфейс и передача
ML-разработчику: [DATA_WEATHER.md](docs/DATA_WEATHER.md).

Отдельно работают **Kelmarsh MODE A** на реальной наблюдаемой SCADA-погоде и
синтетическое автономное демо. Они не заменяют оцениваемый прогноз Goldwind за февраль 2026.
Подробности: [основной контракт](docs/TARGET_FORECAST_CONTRACT.md),
[приёмка по требованиям ТЗ](docs/TARGET_ACCEPTANCE.md).

## Основной сценарий T1/T2: готовность и запуск

**Расписание команды зафиксировано:** первый origin — `2026-01-31T23:00:00+05:00`
(`18:00 UTC`), затем ежедневно в 23:00 Asia/Almaty; первый прогнозируемый час —
00:00 следующего дня. [Решение и граница обучения B](docs/FORECAST_SCHEDULE_DECISION.md).
Это выбор календаря проекта, а не подтверждение timezone и единиц исходных CSV.

После [установки](#установка) выполните:

```bash
python scripts/run_target_forecast.py --check
streamlit run src/app/streamlit_app.py
```

`--check` печатает готовность конфигурации и конкретные блокеры без расчёта мощности.
Код завершения `2` ожидаем, пока обязательные входы отсутствуют. Проверка готовности
не доказывает доступность каждого исторического погодного выпуска: это проверяется
дополнительно при расчёте.

UI по умолчанию открывает **«Прогноз ВЭС T1/T2»**. Пока конфигурация не подтверждена,
он показывает блокеры и отключает кнопку расчёта. Значение времени в форме —
редактируемый технический пример, а не подтверждённое расписание организаторов.

Для основного запуска нужны:

1. Подтверждённый протокол в `config/forecast_protocol.json`: timezone, локальный час
   ежедневного запуска, первый lead, метка начала часового интервала, определение
   нормализованной мощности и основание подтверждения от организаторов.
2. Провайдер архивных прогнозов с временем выпуска и доступности **конкретной версии**
   данных, единицами, высотой ветра и источником. Реанализ, наблюдения и синтетика
   в основном сценарии не принимаются.
3. Целевая модель T1/T2 и manifest: SHA-256 артефакта, признаки, единицы, происхождение
   обучающей выборки, границы обучения/подбора и время доступности использованных данных.

Не переключайте `confirmed` для обхода блокера. Протокол должен отражать реальные
сведения организаторов. Модель не должна использовать данные, недоступные на origin.
Интерфейсы A/B и manifest описаны в [TARGET_FORECAST_CONTRACT.md](docs/TARGET_FORECAST_CONTRACT.md).

| Переменная | Назначение |
| --- | --- |
| `FORECAST_DATA_MODULE` | Модуль архивных погодных выпусков по основному контракту |
| `FORECAST_ML_MODULE` | Модуль целевой модели, возвращающий raw кВт |
| `FORECAST_MODEL_PATH` | По умолчанию `models/goldwind/power_model.joblib` |
| `FORECAST_MANIFEST_PATH` | По умолчанию `models/goldwind/forecast_manifest.json` |
| `FORECAST_PROTOCOL_PATH` | По умолчанию `config/forecast_protocol.json` |
| `FORECAST_CACHE_DIR` | По умолчанию `data/cache/forecast_v2` |
| `FORECAST_RESULTS_DIR` | По умолчанию `results/forecast_v2` |

После подключения входов задайте переменную `FORECAST_ORIGIN` подтверждённым моментом
запуска в ISO 8601 с timezone. Формат строки: `YYYY-MM-DDTHH:00:00+HH:MM`;
конкретные дату, час и offset возьмите из подтверждённого протокола, не из примера UI.

```bash
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 48 --output results/target.json
# Горизонт 24 часа и повторная проверка допустимых погодных обновлений:
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 24 --refresh
# Необязательный анализ через OpenAI:
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 48 --with-agent
```

Результат сохраняет `forecast_origin`, `weather_issued_at`, `weather_available_at`,
`valid_time`, `lead_hours`, версии модели/погоды, T1/T2 и почасовую сумму станции.
`valid_time` обозначает начало интервала. Хранение и графики используют UTC;
это не предположение о timezone исходных SCADA.

Raw-прогнозы не обрезаются. Отрицательные значения, превышение номинала и пропуски
видны в флагах. Сумма ВЭС считается только для совпадающих origin/valid_time.
Если турбина отсутствует или физически невалидна, мощность/энергия ВЭС
равна `null`, а не сумме с искусственным нулём. Для честных метрик сохраняется
отдельная `raw_power_kw`, если обе raw-мощности конечны. Энергия за час — кВт × 1 ч.

Обновление источника выполняется через `--refresh` или переключатель UI.
Изменившиеся допустимые версии/хэши входов дают новую версию расчёта; старые результаты
сохраняются. Более поздний выпуск не допускается в старый origin даже при обновлении
кэша. Неизменившиеся входы используют сохранённый результат без лишних LLM-запросов.
Автономное расписание опроса внешнего API и production deployment пока не настроены.

## Основной исторический replay февраля 2026

```bash
python scripts/replay_february.py --horizon 48 --output-dir results/february-48h
python scripts/replay_february.py --horizon 24 --output-dir results/february-24h
# Только если организаторы предоставили реальные почасовые факты февраля:
python scripts/replay_february.py --horizon 48 --actuals data/actuals.csv --output-dir results/february-with-actuals
```

Origins идут ежедневно **с 31 января по 28 февраля включительно** в локальном часу
подтверждённого протокола. Для оценки учитываются часы с 1 февраля включительно
до 1 марта исключительно в том же timezone. Часы вне февраля сохраняются,
но не включаются в февральские метрики.

Выход: `predictions.csv`, `farm.csv`, `manifest.json`. Manifest содержит конфигурацию,
готовность, run IDs, версии и SHA-256 файлов, покрытие, ошибки и метрики.
Все origins и перекрытия сохраняются: лучший выпуск постфактум не выбирается.
Покрытие отдельно показывает число прогнозных строк и уникальных часов,
конечные raw-значения и физически полные часы станции.

Actuals CSV: `timestamp,turbine_id,actual_power_kw`. Timestamp имеет timezone и
обозначает **начало часа**; мощность — средние raw кВт за час; ID — T1 или T2.
Дубликаты, нечисловые и бесконечные значения отклоняются. Конечные отрицательные
значения не обрезаются. Для факта станции требуются обе турбины.
Метрики используют все совпавшие конечные raw-пары, включая физические флаги,
и группируются по турбине, lead и первым/вторым 24 часам.

Без фактов метрики `null`. Без обязательной конфигурации получаются blocked manifest
и CSV только с заголовками — фиктивные прогнозы не создаются. Ошибка отдельного origin
не останавливает последующие; blocked/partial replay возвращает код `2`.
Полный реальный февральский replay пока не подтверждён.

После установки зависимостей:

В боковом меню UI выберите «Реальные данные Kelmarsh», затем турбину и дату,

покрытие, флаги и анализ. Данные сохранены в репозитории; ключи и переобучение не нужны.

Реестр: `config/kelmarsh_turbines.json`; шесть Senvion MM92 по 2050 кВт,
высота 78,5 м (1/2/4/5) или 68,5 м (3/6). Это отдельная станция, не T1/T2.
Период полных суток holdout: **2017-11-08…2017-12-31**, горизонт 1–72 ч должен помещаться в него.
Сохраняется исходный шаг **10 минут**. Энергия — оценка суммы кВт × 10/60 ч,
не показание счётчика; start/end convention timestamp источника не подтверждён.
Пропуски и невалидная мощность делают полный итог энергии null, значения не обрезаются.
Метрики используют все конечные пары raw/actual, включая отрицательные и выше номинала,
в соответствии с протоколом B. Это MODE A по наблюдаемой погоде, не прогноз будущего.

Проверка неизменности artifact/holdout и воспроизведения метрик B:

```bash
python -m scripts.verify_ml_provider --report results/provider_verification.json
```

На всех 47006 holdout-строках: raw MAE **82,9047 кВт**, RMSE **145,1903 кВт**,
R² **0,953016**. Метрики выбранной турбины/дня отличаются от общей оценки.
Дневной backtest сохраняет results.csv, summary.json и daily.json в results/observed-backtest.
При пропусках покрытия CLI возвращает код 2, сохраняя результаты и описание пропусков.
LLM опционален через `--with-agent` (до одного запроса на день).

## Что реализовано

- Orchestrator: валидация → погода/кэш → признаки → локальная модель → статистика → правила → анализ.
- Контракты Person A (DATA) и Person B (ML), импорт через настройки без зависимости агента от модели.
- Structured Output через официальный OpenAI Python SDK, `responses.parse` и Pydantic.
- Один короткий запрос анализа на запуск; в backtest — на день только при `--with-agent`.
- Локальный fallback без ключа, при отказе API, таймауте или некорректном ответе; автоматические retries отключены.
- Правила: пропуски/NaN, невозможная погода, отрицательная/выше номинала мощность,
  скачки более 50% номинала, сильный ветер ниже cut-out при почти нулевой генерации.
- CLI, backtest с CSV/JSON, Streamlit UI, FastAPI с `/forecast` и `/health`.
- Основной `src/forecast`: доступность погодного выпуска и обучающих данных на origin,
  24/48 часов, сумма ВЭС, версии входов, пересчёт, февральский rolling replay.
- Основные API `/readiness` и `/target-forecast`; UI по умолчанию показывает целевой сценарий и блокеры.
- Сохранённые синтетические данные и локальная demo ML-модель; сеть для demo не нужна.

Технологии: Python 3.12, pandas, NumPy, scikit-learn/joblib, Pydantic, OpenAI SDK,

синтетических примеров идеализированной кривой мощности. Это проверка pipeline,
а не валидированная модель Goldwind.

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock.txt
cp .env.example .env
```

`requirements.lock.txt` фиксирует проверенное окружение Python 3.12/macOS arm64;

При смене версии scikit-learn перегенерируйте только demo-артефакты:

## Демо за 30 секунд после установки

```bash
python scripts/run_forecast.py --demo --date 2026-02-10 --turbine T1 --horizon 24 --output results/demo.json
```

CLI печатает структурированный JSON: 24 точки мощности и ветра, энергию, флаги и анализ.
Информационные логи идут в stderr. Exit code 0 — полный валидный прогноз, 2 — ошибка/неполное покрытие.
Демо поддерживает даты **2026-01-31…2026-02-28**, горизонт 1–72 ч, T1/T2.
Обе турбины используют один синтетический ряд — пространственные различия не моделируются.

```bash
streamlit run src/app/streamlit_app.py
```

В UI выберите турбину и дату, нажмите «Рассчитать прогноз». Появятся мощность,

по умолчанию UI показывает основной сценарий «Прогноз ВЭС T1/T2».
Демо включается явно и не подставляется вместо отсутствующего целевого прогноза.

| --- | --- |
| `OPENAI_API_KEY` | Ключ команды, только через окружение/.env |
| `OPENAI_MODEL` | Доступная команде модель с Responses Structured Outputs; дефолта нет |
| `DEMO_MODE` | `true` для offline demo; по умолчанию `false` |
| `DATA_MODULE` | Python-модуль Person A с get_archival_weather/build_features |
| `ML_MODULE` | Python-модуль Person B с load_model/predict |
| `MODEL_PATH` | Локальный путь модели; по умолчанию models/production |
| `TURBINES_FILE` | По умолчанию config/turbines.json |
| `WEATHER_CACHE_DIR` | По умолчанию data/cache |

`DATA_MODULE`, `ML_MODULE`, `MODEL_PATH`, `WEATHER_CACHE_DIR` и `DEMO_MODE` относятся
к старому интерфейсу/demo. Основной прогноз использует отдельные `FORECAST_*` из раздела выше.

```bash
python scripts/run_forecast.py --demo --date 2026-02-10 --with-agent
```

`--with-agent` разрешает один API-запрос при наличии ключа и модели. Для demo агент
по умолчанию локальный; для обычного CLI-прогноза OpenAI включён при конфигурации.
`--no-agent` отключает API. SDK проверен: openai 2.54.0, callable responses.parse.
Реальный OpenAI-вызов не проверен без ключа/имени модели; SDK-вызов и сценарии отказов
проверены подставными ответами. Использован официальный
[Structured Outputs guide](https://developers.openai.com/api/docs/guides/structured-outputs).

## Старый backtest: demo и совместимость

`scripts/run_forecast.py`, `scripts/run_backtest.py` и API `/forecast` сохранены для
совместимости. **Они не являются основным оцениваемым путём по ТЗ.** Для origin/vintage
сценария используйте `run_target_forecast.py` и `replay_february.py`, описанные выше.

По умолчанию: **31 января — 28 февраля 2026 включительно**, 29 ежедневных запусков,
каждый на 24 часа от 00:00 UTC. LLM по умолчанию выключен.

```bash
python scripts/run_backtest.py --demo
python scripts/run_backtest.py --demo --turbine T2 --output-dir results/backtest-t2
# После подключения реальных провайдеров и фактов:
python scripts/run_backtest.py --actuals data/actuals.csv
# Опционально: до одного запроса LLM на день
python scripts/run_backtest.py --demo --with-agent
```

Выход: `results/backtest/results.csv`, `summary.json`, а с агентом — `analyses.json`.
Actuals CSV: `timestamp,turbine_id,actual_power_kw`; timestamp с UTC offset,
мощность — средняя за часовую ячейку. Сопоставление строго по турбине и времени.
Дубликаты и некорректные actuals отклоняются; пропуски не заполняются нулями.
Метрики MAE/RMSE/bias выводятся только при наличии совпавших валидных actuals, вместе с покрытием.
Без фактов метрики `null`. Ошибки отдельных дней записываются, прогон продолжается,
а exit code 2 не даёт спутать неполный backtest с успешным.

## Data/API и интеграция

Основной контракт: [TARGET_FORECAST_CONTRACT.md](docs/TARGET_FORECAST_CONTRACT.md).
После запуска `uvicorn src.api.main:app --host 127.0.0.1 --port 8000`:

- `GET /readiness` — готовность конфигурации T1/T2 и блокеры;
- `POST /target-forecast` — поля `forecast_origin` с timezone, `horizon_h` (24/48),
  `refresh`, `with_agent`; возвращает турбины, сумму ВЭС, provenance и статус;
- `GET /health` — только работоспособность API, не готовность прогноза.

Ниже описан старый интерфейс, оставленный для demo и совместимости.

Подробные [контракты](docs/CONTRACTS.md) и [порядок интеграции веток](docs/INTEGRATION.md).
Провайдер Person A должен отдавать ветер на 80 м и происхождение данных.
Кэш различает координаты, модуль, дату выпуска и горизонт. Сохранённый запрос работает
при недоступности API; при отсутствии кэша production возвращает понятную ошибку.
Демо не обращается к погодному API и не подставляется молча в production.

```bash
DEMO_MODE=true uvicorn src.api.main:app --host 127.0.0.1 --port 8000
curl -X POST http://127.0.0.1:8000/forecast \
  -H 'Content-Type: application/json' \
  -d '{"turbine_id":"T1","forecast_date":"2026-02-10","horizon_h":24}'
```

Дополнительно `POST /observed` принимает `{"turbine_id":"Kelmarsh 1","observation_date":"2017-11-08","horizon_h":24}`
и возвращает native samples, actuals, raw metrics и анализ.

API `?with_agent=true` включает анализ; по умолчанию внешних LLM-вызовов нет.
API/UI рассчитаны на локальную демонстрацию; аутентификация для публичного сервиса не реализована.
Deployment URL отсутствует.

## Проверка

```bash
python -m pytest -q
python scripts/run_target_forecast.py --check
python scripts/run_forecast.py --demo --date 2026-02-10 --output results/demo.json
python scripts/run_backtest.py --demo
```

Тесты проверяют интеграцию MODE A и demo, единицы/границы мощности, выравнивание времени, пропуски,
контракты признаков, высоту ветра, cache hit при отказе API, отсутствие погодной утечки
из будущего, structured analysis/fallback, actual join/метрики, частичные прогоны и API.
UI дополнительно проверяется Streamlit AppTest.

Новые проверки основного пути включают запрет поздних погодных выпусков и утечки
обучения, 24/48 часов и lead, версии входов и повторный расчёт, сумму T1/T2,
отсутствие фиктивных прогнозов при блокере и сохранение перекрывающихся origins.
Подставные источники в тестах доказывают поведение кода, а не доступность реального
архива или качество Goldwind. Результаты: [TARGET_ACCEPTANCE.md](docs/TARGET_ACCEPTANCE.md).

## Честная демонстрация за 30–60 секунд

1. Открыть **«Прогноз ВЭС T1/T2»** и показать готовность. Пока входы не подключены,
   назвать блокеры и показать, что система не подменяет основной прогноз синтетикой.
2. Переключить **«Реальные данные Kelmarsh»**, выбрать `Kelmarsh 1`, `2017-11-08`,
   нажать «Рассчитать и сравнить». Показать график, факт, метрики, флаги и объяснение.
   Назвать это проверкой интеграции на наблюдаемой погоде другой станции.
3. Показать основной контракт и команду февральского replay. После подключения A/B
   вместо блокеров показать T1/T2, сумму ВЭС, времена выпуска/доступности и manifest
   реального replay. До этого не объявлять основное ТЗ выполненным.

## Ограничения и оставшаяся работа

- Подтвердить timezone, timestamp, normalized power и происхождение полученного экспорта T1/T2.
  ML-ветка B интегрирована для Kelmarsh; целевая обученная модель Goldwind не подключена.
- Подключить реальный архив выпусков погоды, проверить доступность каждого выпуска
  и границы доступности данных модели. Реанализ не заменяет архивный прогноз.
- Выполнить реальный сквозной прогноз и февральский replay; метрики считать только
  при наличии фактической генерации февраля.
- Пороговые скорости 3/25 м/с — предварительные настройки, не подтверждённые характеристики GW109.
- Нет вероятностных интервалов, калибровки неопределённости, SCADA/curtailment/maintenance контекста.
- Сумма станции и пересчёт обновлённых входов реализованы; автономное расписание
  опроса источников и production deployment пока не настроены.
- Прогноз — почасовая средняя мощность, поэтому сумма × 1 ч даёт кВт·ч.
  При некорректных часах полная энергия `null`, а не искусственно заниженная сумма.
- Детерминированные флаги — основания для проверки, не диагноз поломки.
- OpenAI улучшает объяснение; численные результаты и локальный fallback работают без него.
