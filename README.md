## Основной сценарий T1/T2: готовность и запуск

**Расписание команды зафиксировано:** первый origin — `2026-01-31T23:00:00+05:00`
(`18:00 UTC`), затем ежедневно в 23:00 Asia/Almaty; первый прогнозируемый час —
00:00 следующего дня. [Решение и граница обучения B](docs/FORECAST_SCHEDULE_DECISION.md).
Это выбор календаря проекта, а не подтверждение timezone и единиц исходных CSV.

После [установки](#установка) выполните:

```bash
python scripts/run_target_forecast.py --check
streamlit run src/app/streamlit_app.py
```

`--check` печатает готовность конфигурации и конкретные блокеры без расчёта мощности.
Код завершения `2` ожидаем, пока обязательные входы отсутствуют. Проверка готовности
не доказывает доступность каждого исторического погодного выпуска: это проверяется
дополнительно при расчёте.

UI по умолчанию открывает **«Прогноз ВЭС T1/T2»**. Пока конфигурация не подтверждена,
он показывает блокеры и отключает кнопку расчёта. Значение времени в форме —
редактируемое расписание команды из `config/forecast_schedule.json`; оно не задаёт timezone исходных CSV.

Для основного запуска нужны:

1. Подтверждённый протокол в `config/forecast_protocol.json`: timezone, локальный час
   ежедневного запуска, первый lead, метка начала часового интервала, определение
   нормализованной мощности и основание подтверждения от организаторов.
2. Провайдер архивных прогнозов с временем выпуска и доступности **конкретной версии**
   данных, единицами, высотой ветра и источником. Реанализ, наблюдения и синтетика
   в основном сценарии не принимаются.
3. Целевая модель T1/T2 и manifest: SHA-256 артефакта, признаки, единицы, происхождение
   обучающей выборки, границы обучения/подбора и время доступности использованных данных.

Не переключайте `confirmed` для обхода блокера. Протокол должен отражать реальные
сведения организаторов. Модель не должна использовать данные, недоступные на origin.
Интерфейсы A/B и manifest описаны в [TARGET_FORECAST_CONTRACT.md](docs/TARGET_FORECAST_CONTRACT.md).

| Переменная | Назначение |
| --- | --- |
| `FORECAST_DATA_MODULE` | По умолчанию `src.data.weather` (A) |
| `FORECAST_ML_MODULE` | По умолчанию `src.ml.goldwind_provider` (B), raw кВт |
| `FORECAST_MODEL_PATH` | По умолчанию `models/goldwind/power_model.joblib` |
| `FORECAST_MANIFEST_PATH` | По умолчанию `models/goldwind/forecast_manifest.json` |
| `FORECAST_PROTOCOL_PATH` | По умолчанию `config/forecast_protocol.json` |
| `FORECAST_CACHE_DIR` | По умолчанию `data/cache/forecast_v2` |
| `FORECAST_RESULTS_DIR` | По умолчанию `results/forecast_v2` |

После подтверждения входных данных используйте расписание команды:

```bash
FORECAST_ORIGIN=2026-01-31T23:00:00+05:00
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 48 --output results/target.json
# Горизонт 24 часа и повторная проверка допустимых погодных обновлений:
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 24 --refresh
# Необязательный анализ через OpenAI:
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 48 --with-agent
```

Результат сохраняет `forecast_origin`, `weather_issued_at`, `weather_available_at`,
`valid_time`, `lead_hours`, версии модели/погоды, T1/T2 и почасовую сумму станции.
`valid_time` обозначает начало интервала. Хранение и графики используют UTC;
это не предположение о timezone исходных SCADA.

Raw-прогнозы не обрезаются. Отрицательные значения, превышение номинала и пропуски
видны в флагах. Сумма ВЭС считается только для совпадающих origin/valid_time.
Если турбина отсутствует или физически невалидна, мощность/энергия ВЭС
равна `null`, а не сумме с искусственным нулём. Для честных метрик сохраняется
отдельная `raw_power_kw`, если обе raw-мощности конечны. Энергия за час — кВт × 1 ч.

Обновление источника выполняется через `--refresh` или переключатель UI.
Изменившиеся допустимые версии/хэши входов дают новую версию расчёта; старые результаты
сохраняются. Более поздний выпуск не допускается в старый origin даже при обновлении
кэша. Неизменившиеся входы используют сохранённый результат без лишних LLM-запросов.
Автономное расписание опроса внешнего API и production deployment пока не настроены.

## Основной исторический replay февраля 2026

```bash
python scripts/replay_february.py --horizon 48 --output-dir results/february-48h
python scripts/replay_february.py --horizon 24 --output-dir results/february-24h
# Только если организаторы предоставили реальные почасовые факты февраля:
python scripts/replay_february.py --horizon 48 --actuals data/actuals.csv --output-dir results/february-with-actuals
```

Origins идут ежедневно **с 31 января по 28 февраля включительно** в локальном часу
подтверждённого протокола. Для оценки учитываются часы с 1 февраля включительно
до 1 марта исключительно в том же timezone. Часы вне февраля сохраняются,
но не включаются в февральские метрики.

Выход: `predictions.csv`, `farm.csv`, `manifest.json`. Manifest содержит конфигурацию,
готовность, run IDs, версии и SHA-256 файлов, покрытие, ошибки и метрики.
Все origins и перекрытия сохраняются: лучший выпуск постфактум не выбирается.
Покрытие отдельно показывает число прогнозных строк и уникальных часов,
конечные raw-значения и физически полные часы станции.

Actuals CSV: `timestamp,turbine_id,actual_power_kw`. Timestamp имеет timezone и
обозначает **начало часа**; мощность — средние raw кВт за час; ID — T1 или T2.
Дубликаты, нечисловые и бесконечные значения отклоняются. Конечные отрицательные
значения не обрезаются. Для факта станции требуются обе турбины.
Метрики используют все совпавшие конечные raw-пары, включая физические флаги,
и группируются по турбине, lead и первым/вторым 24 часам.

Без фактов метрики `null`. Без обязательной конфигурации получаются blocked manifest
и CSV только с заголовками — фиктивные прогнозы не создаются. Ошибка отдельного origin
не останавливает последующие; blocked/partial replay возвращает код `2`.
Полный реальный февральский replay пока не подтверждён.

## Что реализовано

- Orchestrator: валидация → погода/кэш → признаки → локальная модель → статистика → правила → анализ.
- Контракты Person A (DATA) и Person B (ML), импорт через настройки без зависимости агента от модели.
- Structured Output через официальный OpenAI Python SDK, `responses.parse` и Pydantic.
- Один короткий запрос анализа на запуск; в backtest — на день только при `--with-agent`.
- Локальный fallback без ключа, при отказе API, таймауте или некорректном ответе; автоматические retries отключены.
- Правила: пропуски/NaN, невозможная погода, отрицательная/выше номинала мощность,
  скачки более 50% номинала, сильный ветер ниже cut-out при почти нулевой генерации.
- CLI, backtest с CSV/JSON, Streamlit UI, FastAPI с `/forecast` и `/health`.
- Основной `src/forecast`: доступность погодного выпуска и обучающих данных на origin,
  24/48 часов, сумма ВЭС, версии входов, пересчёт, февральский rolling replay.
- Основные API `/readiness` и `/target-forecast`; UI по умолчанию показывает целевой сценарий и блокеры.
- Сохранённые синтетические данные и локальная demo ML-модель; сеть для demo не нужна.

Полученные файлы лежат в [data/goldwind/incoming/received_20260923](data/goldwind/incoming/received_20260923). В основном CSV — **50 784 почасовые строки** с метками T1/T2 за **11.03.2023–31.01.2026**. Данные 1–10 марта отсутствуют. До финального обучения автор CSV или организаторы должны подтвердить:

- timezone и историческую политику перевода часов, начало/конец интервала;
- единицы ветра, температуры и мощности, формулу нормализации и её знаменатель;
- соответствие исходных меток физическим T1/T2;
- метод агрегации, смысл `sample_count`, пропусков, остановок и предварительной очистки;
- высоту/место измерения ветра и время доступности SCADA;
- точный первый `forecast_origin` с часовым поясом и согласованное расписание запусков.

Диапазон значений не позволяет достоверно восстановить эти определения. Исходные CSV сохраняются для аудита. Подробности: [проверка поставки](docs/GOLDWIND_DELIVERY_REVIEW.md), [машинный отчёт](reports/goldwind_delivery_audit.json).

## Goldwind: условия запуска

```bash
python scripts/run_target_forecast.py --check
```

Команда возвращает готовность конфигурации и блокеры; код `2` ожидаем при отсутствии обязательных входов. Такая проверка не заменяет проверку исторической доступности каждого выпуска погоды.

Для реального расчёта требуются:

1. Подтверждённый [forecast protocol](config/forecast_protocol.json): timezone, час запуска, первый lead, интервальная и целевая семантика. `confirmed` нельзя включать без основания.
2. Архивные прогнозы погоды с фактическими `weather_issued_at`, `weather_available_at`, `valid_time`, моделью/продуктом, версией, высотой ветра и временным шагом. Доступность проверяется для конкретной ревизии на момент origin. Успешная загрузка файла этого не доказывает; реанализ и наблюдения не заменяют прогноз, доступный в прошлом.
3. Отдельная модель, обученная на подтверждённых данных Goldwind, и manifest с SHA-256, входной схемой, единицами, происхождением данных, границами fit/selection и их доступностью. Все использованные данные должны быть доступны не позже первого origin.

Подготовленные в PR #5 обучение и провайдер используют скорость ветра, температуру, календарные признаки и явный ID турбины. Направление ветра не обязательно. План оценки: mean baseline и sklearn HistGradientBoosting, временная валидация, без февраля 2026 в подборе. Преобразования сохраняются внутри pipeline; провайдер возвращает raw кВт без clipping. Команды обучения приведены в этом PR и станут доступны в `main` после его интеграции.

| Переменная окружения | Назначение |
| --- | --- |
| `FORECAST_DATA_MODULE` | Подключаемый провайдер архивных выпусков погоды |
| `FORECAST_ML_MODULE` | Провайдер целевой модели; планируемый модуль из PR #5 — `src.ml.goldwind_provider` |
| `FORECAST_MODEL_PATH` | `models/goldwind/power_model.joblib` — целевой artifact пока отсутствует |
| `FORECAST_MANIFEST_PATH` | `models/goldwind/forecast_manifest.json` — создаётся с целевым artifact |
| `FORECAST_PROTOCOL_PATH` | `config/forecast_protocol.json` |
| `FORECAST_CACHE_DIR` | `data/cache/forecast_v2` |
| `FORECAST_RESULTS_DIR` | `results/forecast_v2` |

После подтверждения протокола и подключения входов задайте `FORECAST_ORIGIN` точным согласованным временем в ISO 8601 с UTC offset. Следующие команды используют эту переменную Bash:

```bash
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 48 --output results/target.json
python scripts/run_target_forecast.py --origin "$FORECAST_ORIGIN" --horizon 24 --refresh
```

Результат хранит origin, время выпуска и доступности погоды, начало прогнозного часа, lead, версии входов, значения T1/T2 и сумму ВЭС. Raw-мощность сохраняется до физических проверок. Отрицательные значения и превышение номинала получают флаги. При отсутствии или невалидности одной турбины мощность/энергия станции — `null`; конечная raw-сумма сохраняется отдельно для метрик. Почасовая энергия равна средней мощности × 1 час.

`--refresh` проверяет допустимые обновления и создаёт новую версию результата при изменении входов. Более поздний выпуск не допускается в старый origin. Автономное расписание опроса внешних API пока не настроено. Точный контракт: [TARGET_FORECAST_CONTRACT.md](docs/TARGET_FORECAST_CONTRACT.md).

## Февральский replay и оценка качества

**MODE A:** наблюдаемая погода → мощность. Оценивает зависимость мощности от погодных признаков.

**MODE B:** архивный прогноз погоды → мощность. Оценивает погоду и ML-модель как полную прогнозную систему. Метрики этих режимов не взаимозаменяемы.

После подключения целевых входов:

```bash
python scripts/replay_february.py --horizon 48 --output-dir results/february-48h
python scripts/replay_february.py --horizon 24 --output-dir results/february-24h
# Только при наличии реальных фактов организаторов:
python scripts/replay_february.py --horizon 48 --actuals data/actuals.csv --output-dir results/february-evaluated
```

Origins идут ежедневно с **31 января по 28 февраля 2026 включительно** в часу подтверждённого протокола. Февральские метрики учитывают только интервалы с 1 февраля до 1 марта в том же timezone. Все origins и перекрывающиеся прогнозы сохраняются; лучший выпуск постфактум не выбирается.

Выход: `predictions.csv`, `farm.csv`, `manifest.json` с покрытием, версиями, хэшами и ошибками. Actuals CSV должен содержать `timestamp,turbine_id,actual_power_kw`: timestamp с timezone означает начало часа, мощность — средние raw кВт, ID — T1/T2. MAE/RMSE считаются по совпавшим конечным raw-парам с указанием покрытия.

**Факты февраля нужны для метрик, но не для выпуска прогноза.** Если это скрытая тестовая выборка организаторов, собственные февральские метрики остаются неизвестными (`null`). Пока отсутствуют обязательные входы, replay создаёт blocked manifest и CSV с заголовками; это не готовый прогноз. Реальный полный февральский запуск пока не подтверждён.

## Kelmarsh: воспроизводимый пример на реальных данных

Шесть Senvion MM92 по **2050 кВт**, исходный шаг **10 минут**. Модель и holdout уже сохранены; переобучение и погодный API для примера не нужны.

Доступные полные сутки holdout: `2017-11-08`…`2017-12-31`. По всем **47 006** holdout-строкам сохранённый [отчёт проверки](reports/provider_verification.json) воспроизводит raw **MODE A**:

## Архитектура

```text
Погода + происхождение/доступность
    → проверка на forecast_origin
    → признаки → локальная ML-модель → raw кВт
    → физические правила → статистика T1/T2 и ВЭС
    → локальное/LLM-объяснение → API / UI / CSV / JSON
```

| Каталог | Ответственность |
| --- | --- |
| `src/data/` | DATA-контракты, demo и наблюдения Kelmarsh |
| `src/ml/` | ML-preprocessing, модели, загрузка, оценка и провайдер Kelmarsh |
| `src/forecast/` | Временные контракты, архивные выпуски, целевой orchestrator и replay |
| `src/agent/` | Физические правила, статистика, анализ и сценарии совместимости |
| `src/api/` | FastAPI и раздача интерфейса |
| `src/app/web/` | Основной WindAgent UI: HTML/CSS/JavaScript |
| `src/app/streamlit_app.py` | Сохранённый Streamlit UI |
| `config/`, `data/`, `models/`, `reports/` | Протоколы, исходные данные, artifacts и результаты проверки |

Стек: Python, pandas, NumPy, scikit-learn, joblib, matplotlib, Pydantic, FastAPI, Streamlit; OpenAI SDK для опциональных объяснений. Численный прогноз работает локально без cloud ML services.
